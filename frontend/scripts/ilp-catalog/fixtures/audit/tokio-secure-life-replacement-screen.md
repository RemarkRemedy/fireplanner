# Tokio Secure / Life-Replacement Screen

This note records the screen after the non-secure Tokio current-only multi-life cleanup was burned down.

Products screened:

- `tokio-marine-goclassic-secure`
- `tokio-marine-goelite-secure`
- `tokio-marine-harvest-builder-atfuture`

## Conclusion

The remaining Tokio residual is no longer the same multi-life / last-life parser boundary.

- `#goClassic Secure` is already on a different locked-in-value protection-state kernel. Its live residuals are exact monthiversary ratchet timing, loyalty/additional bonus qualification, and change-of-life-assured administration. That is not another cheap attachment to `branch:tokio-current-only-multi-life-life-state`.
- `#goElite Secure` is also a locked-in-value family. Its remaining metadata-only scope is approved locked-in-value reduction handling, payout administration, aggregation limits, and fund/withdrawal operations. The summary wording does not expose the same oldest-life / youngest-life / last-life roster mechanics as the non-secure Tokio advanced-death family.
- `Harvest Builder@Future` is not a multi-life candidate at all in the current summary corpus. Its residual is plain life-replacement administration plus rider / withdrawal / premium-holiday operations.

So the non-secure Tokio current-only multi-life lane is now closed. The remaining Tokio branch is a separate secure / administrative lane rather than more parser-only cleanup on the life-state branch.

## Product Notes

### `#goClassic Secure`

- The modeled corridor already uses `kernel:tokio-locked-in-protection-state`.
- User-entered current Locked-in Policy Value already gives an honest current snapshot of the present ratchet state on the supported surface.
- The unsupported wording is now specific to payout handling beyond the modeled current death-benefit estimate, exact future monthiversary ratchet timing, and change-of-life-assured administration.
- There is no stale `multiple-life last-life settlement` bucket left to clean up.

### `#goElite Secure`

- The modeled corridor already uses `kernel:tokio-locked-in-protection-state`.
- Current snapshots already have a truthful manual-input path for insurer-approved reductions because the supported surface asks for current Locked-in Policy Value and current Adjusted Single Premium.
- Remaining scope is future approved-reduction administration, payout handling, aggregation limits, minimum residual withdrawal rules, and fund operations.
- The summary corpus does not publish a reusable multi-life roster mechanic comparable to the non-secure Tokio advanced-death family.

### `Harvest Builder@Future`

- Remaining metadata-only behaviors are `life-replacement-administration`, rider handling, withdrawal / minimum-account-value enforcement, and premium-holiday resumption administration.
- The current summary wording does not justify a Tokio life-state extension here.

## Recommendation

1. Treat the non-secure Tokio current-only multi-life cleanup lane as exhausted.
2. Treat the secure Tokio screen as effectively exhausted too: the honest current-state boundary fixes for `#goClassic Secure` and `#goElite Secure` are now landed.
3. Treat the remaining Tokio secure products as a locked-in-value / administrative screen, not a continuation of the last-life kernel lane.
4. Only reopen Tokio secure implementation if a narrow executable sub-slice appears inside the locked-in-value family itself.
